# App Map — where the code lives & how to run it

> The **navigation** doc for `web/`: module ownership, route inventory, local setup, build/asset facts.
> *Why* things are designed the way they are lives in [architecture.md](architecture.md) — this doc answers "which file do I open?".

---

## 1. Run it locally
1. Create a Supabase project, run `web/db/schema.sql` in its SQL editor, then apply migrations `001` (agent trigger) and `003` (Storage bucket) separately — see the migration note in [architecture.md](architecture.md#3-data-model-initial-schema).
2. Copy `web/.env.example` → `web/.env.local` and fill the Supabase keys + `ANTHROPIC_API_KEY`.
3. From `web/`: `npm run dev`.

Other scripts: `npm run build` · `npm run lint` · `npm run test` (Vitest, `web/vitest.config.ts`) · `npm run brand` · `npm run brand:wordmark` · `npm run test:brand` (brand assets — see §5) · `npm run check:rls` / `npm run test:rls` (`web/scripts/check-rls.mjs` — fails on any `public` table missing `enable row level security`; see [architecture.md](architecture.md#5-security--privacy-from-day-one)). `npm run test:scripts` (migration-guard unit tests — see §5).
Deploy topology (prod vs. preview Supabase projects) and the promote-to-prod checklist live in [status.md](status.md).

**Training videos** live outside `web/`, in the standalone [`training/`](../training/README.md) package: Playwright drives a locally running app on seeded demo data in the dev database and renders captioned `.mp4` walkthroughs (`cd training && npm run record -- 01-accident-notice`). It has its own `package.json` and tests (`npm test`); nothing in `web/` depends on it.

## 2. Surfaces (`web/src/app/`)
| Route | Who | What |
|---|---|---|
| `/` | public | marketing landing page ("OpenTik"), Hebrew/RTL |
| `/login` | agent | Supabase Auth sign-in |
| `/c/[token]` | client | token-gated collection wizard (no login) |
| `/dashboard` | agent | **one unified claims list** — `ClaimsList.tsx`, one row per claim **including closed** (no separate archive table). A search box (name, or phone/plate by digits, ≥3; matches the client plate and any third-party plate; closed claims show only under "הכל" and only while a search is active), **stage chips with counts** — הכל · צריך אותך · אצל הלקוח · לפני שליחה למבטחת · נשלח למבטחת · ממתין לתשלום · סגורים — and rows ordered by latest activity (link created / client submitted / document uploaded / an inbound insurer email filed on the claim / handling status changed) with a "חדש"/"מסמך חדש"/"מייל חדש" badge within a day; the "צריך אותך" chip sorts by overdue days instead. Filter + page mirrored into `?stage=` / `?p=` via `replaceState` (`useUrlStage`/`useUrlPage` in `Pager.tsx`; the old `?tp=` is gone); 25 rows per page (`paginate.ts`). **No send/skip on the list** — reminders live in the cockpit header. `RefreshOnFocus.tsx` (client, `router.refresh()` on tab-visible/focus, throttled to once a minute) picks up activity while the tab sits open. The AI brief only loads when `briefEnabled()` (`web/src/lib/dashboard/flags.ts`, `BRIEF_ENABLED=1`) is on — off by default since 2026-09-27 — and then only adds the 🤖 line; ordering and `needs_action` never depend on it. With it off: no model call, no day-cache read, no `after()` warm; when on, a cold cache renders rules-only immediately, warms the ranking via `after()`, and mounts `BriefAutoRefresh.tsx` (`router.refresh()` at 55s and 115s) |
| `/dashboard/[id]` | agent | claim **cockpit** — a persistent header (identity + one primary next action) over tabs: סקירה (claim facts, classification, tasks, checklist, doc upload, notes, **סכומים** amounts card, and — once any mail has been sent or received on the claim — a **התכתבות** correspondence panel, `CorrespondencePanel.tsx`) / שליחה למבטחת (prepare-and-confirm panel, only shown while there is something to send — can confirm a manual send or, when email is on for the business, send the packet directly from the app via `POST /api/claims/[id]/submission/send`) / טופס ההודעה / קבצים (active tab mirrored in `?tab=`) |
| `/dashboard/settings` | agent | `BusinessDetails.tsx` — the handling business's name/phone/email (the demand-form sender); `/dashboard` only shows a one-line nudge + link here while the name is still empty. When email is on for the business, also `EmailSetup.tsx` — shows the read-only system address, an editable `claims_mailbox` (saved on its own via `PATCH /api/agents/me`, rejecting the system's own domain), the last received date, and M365-redirect-rule setup steps + the insurer domain list for forwarding insurer mail that still lands directly in the business's own inbox |
| `/dashboard/overview` | agent | **סקירה** — aggregates for the owner/clerk, not a claim list: open-stage tiles with money-in-flight (links into `/dashboard?stage=`), a "מחכים למבטחת" aging breakdown (0–14/15–30/31–45/45+ days since sent, oldest 3 claims named) with per-band sums, cycle-time medians (collect → prepare → send → pay, hidden under `MIN_SAMPLE=3`), last-30-vs-previous-30-days counts (opened/closed/paid), and a collection completion rate over the last 90 days. Pure aggregation in `web/src/lib/overview/compute.ts`; amounts are read best-effort and the page degrades to counts-only (a banner explains why) if migration `012` hasn't been applied yet |
| `/dashboard/inbox` | agent | **דואר נכנס** — inbound mail that couldn't be filed on a claim automatically (`web/src/lib/email/load.ts`'s `loadUnmatched`), each with an `AssignClaim` search-and-file action (`POST /api/emails/[id]/assign`); a sidebar badge shows the unmatched count. Hidden from `SidebarNav` when email is off for the business (migration `013` not applied, or the business has no `inbound_alias`) |

`/dashboard`, `/dashboard/[id]`, `/dashboard/overview`, `/dashboard/settings` and `/dashboard/inbox` share one shell, `web/src/app/dashboard/layout.tsx`: a fixed sidebar (logo, `SidebarNav.tsx`, user email + logout) on wide screens, collapsing to a slim top bar with a compact `SidebarNav` (icon-less labels) + logout on narrow ones; each page renders only its own `<main>`. Wide screens also get `TopBar.tsx`, a sticky header over the content with a path breadcrumb (תביעות / פרטי תיק / סקירה / הגדרות, from `usePathname()`) and the global `NewClaimForm` button; narrow screens keep `NewClaimForm` in the page header instead. `NewClaimForm` itself is a toggle button that drops its form/created-link panel below it, so the same component works from either place.

`web/src/app/global-error.tsx` — last-resort screen when the root layout itself throws (client component, brings its own `<html>`/`<body>`); the error itself is reported server-side via `instrumentation.ts`, not here.

The client wizard's own files live in `web/src/components/collection/`: `steps.ts` (the step registry — order, chapters, relevance, completeness; the single source of truth for position), `CollectionWizard.tsx` (state, navigation, uploads, submit), `WizardShell.tsx` (chapter chips / dots / nav chrome + the milestone screen), one component per step under `steps/` with shared inputs in `steps/fields.tsx`, and `FollowupUpload.tsx` (the post-submit upload screen).

## 4. API routes (`web/src/app/api/`)
| Route | Method | Purpose |
|---|---|---|
| `/api/claims` | GET/POST | agent claim list / create |
| `/api/claims/submit` | POST | client submits the wizard → auto-fills the accident notice. Compare-and-set on the claim's status, so of two racing submits exactly one wins; the other (and a retry) gets `409` with a machine-readable `already_submitted` code the wizard treats as success. `503` in production when Supabase isn't configured — never a fake `{ok:true}` for data that wasn't stored. After the response it warms the AI analysis cache (`after()` → `warmAnalysis`) so the agent's first cockpit view doesn't wait on the model |
| `/api/claims/draft` | POST | **client** in-progress wizard state by token → merged into `summary_json.draft` (64 KB cap, `409` once the claim is submitted — compare-and-set on status closes the race with a concurrent submit — `{ok:true, demo:true}` outside production when Supabase isn't configured, `503` in production) |
| `/api/claims/documents` | POST | **client** upload (magic-byte sniffed); `503` in production when Supabase isn't configured (demo `{ok:true}` only outside production) |
| `/api/claims/[id]/documents` | POST | **agent** upload with a type tag |
| `/api/claims/[id]/documents/[docId]` | DELETE · PATCH | agent deletes a document, or re-files it under a different type — hidden on closed claims |
| `/api/claims/[id]/classify` | PATCH | agent confirms the track |
| `/api/claims/[id]/checklist` | PATCH | tick a milestone |
| `/api/claims/[id]/tasks` · `/tasks/[taskId]` | POST · PATCH | ad-hoc agent tasks (`source='manual'`) |
| `/api/claims/[id]/notes` | POST | append to the agent scratchpad |
| `/api/claims/[id]/form-data` | PATCH | agent edits the canonical form fields |
| `/api/claims/[id]/form/[insurer]` | GET | on-demand fill for one insurer |
| `/api/claims/[id]/demand-form` | POST | generate the demand form on demand (optional `{ at_fault_insurer }`); also auto-run in `after()` when `classify` confirms `third_party_report` |
| `/api/agents/me` | GET/PATCH | the handling business's details (`name/phone/email`) — the demand-form sender; edited on `/dashboard/settings`. A `PATCH` carrying `claims_mailbox` is handled on its own (the email setup block saves it independently) — validated, lowercased, rejects the system's own inbound domain |
| `/api/claims/[id]/handling` | PATCH | evidence-gated post-send status transition, or claim closure with a reason — compare-and-set, `409` on a concurrent transition |
| `/api/claims/[id]/submission` | POST | confirm the prepare-and-confirm submission to the insurer — persists the TP at-fault insurer, ticks the track's sent-milestone, sets `handling_status='sent'` |
| `/api/claims/[id]/submission/send` | POST | send the claim packet to the insurer **from the app** — from the business's system address, cc'ing its claims mailbox — then performs the same compare-and-set mark-as-sent as `/submission` above; `503` when email isn't configured (`EMAIL_PROVIDER_API_KEY`/`EMAIL_WEBHOOK_SECRET`/`EMAIL_INBOUND_DOMAIN` or migration `013`) |
| `/api/claims/[id]/amounts` | PATCH | record `demand_amount`/`paid_amount` (migration `012`) — either key, independently, clearable with `null`/`""`; allowed on closed claims too |
| `/api/vehicle/[plate]` | GET | **client** plate → make/model/year from the Ministry of Transport registry (server-side proxy, per-instance memo, `200 {vehicle:null}` on a miss) |
| `/api/reports/funnel` | GET | **agent** wizard funnel (`?days=N`, default 90, max 365) — links sent, `completion_rate` (of all links) vs `completion_rate_of_started` (excludes never-opened links — the wizard-only measure), where abandoned sessions stopped, doc-deferral counts; RLS-scoped, reads existing `claims` rows only, no new table |
| `/api/brief/refresh` | POST | re-run the morning-brief ranking |
| `/api/outbound/events` | POST | record one outbound-queue decision (`sent` / `skipped`) — rejects an unknown `task_key`, RLS ownership probe on the claim, service-role insert into `outbound_events` |
| `/api/inbound/email` | POST | the mail provider's (Resend) webhook — not session-authenticated, the provider's signature is the only credential, checked on the raw body first; `503` when email isn't configured, `401` on a bad signature; otherwise `200` for anything a retry can't improve (stored, duplicate, own mail, unknown alias) and `5xx` so the provider retries. A bounce/failure event is handled separately (`recordDeliveryFailure`) and returns before any claim-filing logic. After storing a message, it best-effort sends the business's `claims_mailbox` a copy (failure is reported but doesn't fail the request — the provider would otherwise redeliver a message that's already stored) |
| `/api/emails/[id]/assign` | POST | file an unmatched inbound message (`claim_id is null`) on one of the business's claims — both ids RLS-probed through the user's client, the write itself via the service client; `409` if the message is already filed |
| `/api/auth/login` · `/api/auth/logout` | POST | session |
| `/api/health` | GET | public schema-drift check: `200 {ok, configured, schema:{expected, actual, status}}` when `public.schema_migrations` has every migration the build was made with (`EXPECTED_SCHEMA_VERSIONS`, baked in `next.config.ts` from `web/db/migrations/`); **503** when behind (`missing:[…]`), table missing, or DB unreachable. No Supabase env → 200 `status:"skipped"` locally, 503 on Vercel production. Logic: `web/src/lib/schema-version.ts`. Curled by `.github/workflows/post-deploy-health.yml` |
| `/api/version` | GET | live build: `{commit (short VERCEL_GIT_COMMIT_SHA, "local" off-Vercel), env (VERCEL_ENV), expectedSchema}` |

The mutation routes (`submit`, `classify`, `checklist`, `documents`, `submission`, `submission/send`, `handling` on a milestone tick) each call `runEngine` inline, best-effort.

## 5. Build & assets
- **Next.js 16** + TypeScript + Tailwind v4, RTL. `next build` passes.
- Hebrew font `web/src/lib/formfill/assets/app-hebrew.ttf` = **Noto Sans Hebrew** static Regular (OFL 1.1, license bundled as `assets/OFL.txt`). Every template renders under it; the original 9 were explicitly re-QA'd at the font swap (כלל + שומרה were mapped later, under the same font).
- Prod asset bundling for the PDF templates/font is configured via `outputFileTracingIncludes` in `web/next.config.ts` — add new bundled assets there or they vanish on Vercel.
- QA a fill locally with `web/scripts/fill.ts` (uses `formfill/sample-claim.ts`).
- Env override: `CLAIMS_AI_MODEL` swaps the analysis model tier.
- **Brand assets** live in `web/public/brand/`; the **SVG masters are the source of truth**. `npm run brand` (`web/scripts/build-brand-assets.mjs`) rasterizes every PNG from them and writes the multi-size `web/src/app/favicon.ico` (16/32/48, PNG-in-ICO) — **never hand-edit a generated PNG**, re-run the script. `npm run brand:wordmark` (`scripts/gen-wordmark.mjs`) regenerates the outlined wordmark/lockup SVGs (text is outlined so rendering needs no font). Rasterizing uses **`sharp` 0.34.5**, which resolves as an *optional transitive* dep of Next — it is not declared in `web/package.json`.
- `npm run test:brand` runs `node --test scripts/__tests__/brand-assets.test.mjs` (asserts master-SVG invariants + rendered PNG sizes) — a **separate runner from Vitest**, so `npm run test` does not cover it. `npm run test:rls` runs the sibling `scripts/__tests__/check-rls.test.mjs` the same way (own script, not a glob, since both now live under `scripts/__tests__/`).
- `npm run test:scripts` runs `scripts/__tests__/migration-guard.test.mjs` (unit tests for `.github/scripts/migration-guard.cjs`) the same way.
